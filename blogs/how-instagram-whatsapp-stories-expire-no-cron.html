How Instagram & WhatsApp Stories Expire in Exactly 24 Hours: Does a Cron Job Actually Run?

Harshit Joshi

Gyaan Ki Baat #16 • 15 min read • Published Aug 2026

Every day, over 500 Million Daily Active Users (DAU) post more than 1 Billion ephemeral Stories and Status updates on Instagram, WhatsApp, and Facebook. Exactly 24 hours (86,400 seconds) after publication, the story vanishes from the user's tray, becomes inaccessible to friends, and disappears from feeds worldwide.

If you ask a junior developer how this works, the most common answer is: "A cron job runs every minute and deletes all records where created_at < NOW() - 24 hours."

In this deep-dive, we break down why a database cron job would bring a distributed system to its knees in seconds, and uncover the real 4-tier architecture powering 24-hour expiration at hyper-scale: Lazy Evaluation, Redis TTL Probabilistic Eviction, Hierarchical Timing Wheels, and $O(1)$ Time-Partitioned Database Drops.

Figure 1: High-level architectural pipeline of 24h story expiration: Client queries, Redis TTL, Timing Wheels, and Time-Partitioned Drops.

1. The Naive Approach: Why Cron Jobs Fail at Scale

Imagine a background worker executing this SQL query every 60 seconds across a cluster storing 1,000,000,000 active story rows:

Naive Cron Approach (Crashes Databases at Scale) 
-- Runs every minute via cron / scheduler
DELETE FROM user_stories 
WHERE created_at < NOW() - INTERVAL '24 hours';

Here is what actually happens when you run this at Meta/Instagram scale:

  • Table & Row Lock Contention: A DELETE statement scanning and locking millions of rows across B-Tree indexes blocks incoming user writes and timeline reads.
  • WAL & Binlog Flooding: In relational databases (PostgreSQL/MySQL), every single row deletion generates a Write-Ahead Log (WAL) or binary replication log entry. Deleting 700,000 stories every minute saturates replication network bandwidth and causes massive replication lag on read-replicas.
  • Dead Tuple Bloat & Disk Fragmentation: In MVCC databases (Postgres), DELETE doesn't free disk space immediately; it writes a delete mask (dead tuple), requiring relentless background VACUUM jobs that consume 100% of server CPU and NVMe disk I/O.
  • The "Thundering Herd" Spike: At the top of every minute (`:00`), CPU utilization spikes to 100%, causing latency spikes (P99 > 5,000ms) for real-time user requests.

2. Layer 1: Read-Time Filtering & Lazy Expiration (Zero DB Deletes)

The first law of high-throughput distributed systems is: Never do background work if you can defer it to read time.

When you open Instagram and your phone fetches your friends' story trays, the system does not need a background cleaner to have physically purged expired stories from the disk. Instead, the API gateway and feed services perform Logical Soft Filtering:

feed_service.go (Logical Read-Time Expiration) 
type Story struct {
    ID        string    `json:"id"`
    UserID    string    `json:"user_id"`
    MediaURL  string    `json:"media_url"`
    CreatedAt time.Time `json:"created_at"`
    ExpiresAt time.Time `json:"expires_at"` // Set to CreatedAt + 24 Hours
}

// FetchActiveStories filters out expired stories on-the-fly in O(1)
func FetchActiveStories(stories []Story) []Story {
    now := time.Now()
    active := make([]Story, 0, len(stories))

    for _, s := range stories {
        // If current time exceeds expiration timestamp, silently omit
        if s.ExpiresAt.After(now) {
            active = append(active, s)
        }
    }
    return active
}

Dynamic Edge CDN Caching via Remaining TTL

When media (photos, video segments) is uploaded to Meta's Origin Storage / CDN, the Origin injects a calculated Cache-Control header with the exact remaining seconds until expiration:

HTTP Response Header (Origin CDN) 
HTTP/2 200 OK
Content-Type: video/mp4
Date: Fri, 28 Aug 2026 14:00:00 GMT
Expires: Sat, 29 Aug 2026 14:00:00 GMT
Cache-Control: public, max-age=86400, s-maxage=86400

If a user requests the video 6 hours after posting, the CDN calculates s-maxage = 64800 (18 hours remaining). When the 24-hour mark arrives, edge CDN points across the globe automatically evict the media without the origin server ever issuing a single cache-purge broadcast!

3. Layer 2: In-Memory Caching (Redis TTL Internals)

Active story metadata and user trays are cached entirely in RAM across distributed Redis clusters (or Meta's internal TAO / Memcached fleet). When a story is published, a key is written with an explicit Time-To-Live (TTL):

Redis TTL Setup 
# Set story metadata with 86400 seconds (24 hours) TTL
SET story:metadata:982341 '{"user_id": "harshit", "media": "s3://..."}' EX 86400

# Add to user's active story set
ZADD user:stories:harshit 1787928995 "story:metadata:982341"

How Redis Evicts Millions of Expired Keys Without Blocking

Redis is single-threaded for command execution. If Redis iterated over millions of keys to find expired ones, the entire cache would freeze. Instead, Redis combines two complementary algorithms:

Strategy Trigger Mechanism Complexity & Behavior
1. Passive / Lazy Expiration Client executes GET story:metadata:982341 Redis checks if expire_time < current_time. If expired, Redis instantly deletes the key in $O(1)$ and returns nil. Zero background CPU cost.
2. Active Probabilistic Expiration Internal timer runs 10 times/sec (hz = 10) 1. Samples 20 random keys with TTL.
2. Deletes all expired keys found.
3. If > 25% of sampled keys were expired, it repeats step 1 immediately (capped at 25ms maximum execution time to avoid lag).

4. Layer 3: Event-Driven Triggers via Hierarchical Timing Wheels

What if an asynchronous background side-effect must occur at the exact 24-hour second mark? For example:

  • Auto-archiving the story to the user's private "Memories" archive.
  • Finalizing view counts and viewer impression analytics.
  • Removing story rings from follower graph indexes.

Using a standard Priority Queue (Min-Heap) for 500M timers requires $O(\log N)$ insertion and deletion, which degrades under millions of concurrent writes. High-performance systems use Hierarchical Timing Wheels (popularized by Kafka, Netty, and Linux kernel timer interrupts).

timing_wheel.py (Hierarchical O(1) Expiration Timer Concept) 
class HierarchicalTimingWheel:
    def __init__(self):
        # 60 second buckets (1 tick = 1 sec)
        self.second_wheel = [[] for _ in range(60)]
        # 60 minute buckets (1 tick = 1 min)
        self.minute_wheel = [[] for _ in range(60)]
        # 24 hour buckets (1 tick = 1 hour)
        self.hour_wheel = [[] for _ in range(24)]

    def schedule_expiry(self, story_id, delay_seconds=86400):
        """Schedules story cleanup in O(1) constant time"""
        target_hour = (delay_seconds // 3600) % 24
        self.hour_wheel[target_hour].append(story_id)

    def on_hour_tick(self, current_hour):
        """Cascades pending tasks down to minute and second wheels in O(1)"""
        pending_stories = self.hour_wheel[current_hour]
        self.hour_wheel[current_hour] = []
        for story_id in pending_stories:
            # Cascade to minute/second wheel or emit Kafka Expiration Event
            self.emit_kafka_event("STORY_EXPIRED_EVENT", story_id)

When the timer fires, an event is emitted into an Apache Kafka topic. Consumer microservices asynchronously process the story archive pipeline, invalidate stale secondary caches, and persist analytics without touching the main OLTP database tables.

5. Layer 4: Hard Database Purging via $O(1)$ Time-Partitioned Table Drops

Eventually, cold story records that are days or weeks old must be wiped from persistent primary disks (PostgreSQL / MySQL / Cassandra / ScyllaDB). How do engineering teams perform this without writing millions of individual DELETE statements?

They use Time-Based Range Partitioning:

time_partitioning.sql (Instant O(1) File Drop) 
-- Master Table partitioned by Range of creation timestamp
CREATE TABLE user_stories (
    story_id UUID NOT NULL,
    user_id BIGINT NOT NULL,
    media_url VARCHAR(512),
    created_at TIMESTAMP NOT NULL,
    PRIMARY KEY (created_at, story_id)
) PARTITION BY RANGE (created_at);

-- Each hour or day gets its own physical partition on disk
CREATE TABLE stories_2026_08_27_h14 PARTITION OF user_stories
    FOR VALUES FROM ('2026-08-27 14:00:00') TO ('2026-08-27 15:00:00');

-- TO CLEAN UP: A simple DDL command drops the entire table file in O(1)
ALTER TABLE user_stories DETACH PARTITION stories_2026_08_27_h14;
DROP TABLE stories_2026_08_27_h14;

Why DROP TABLE is $10,000\times$ Faster than DELETE:

  • DELETE scans rows, marks dead tuples, modifies B-Trees, writes gigabytes of WAL logs, and leaves empty space fragmented on disk.
  • DROP TABLE executes an instantaneous filesystem unlink() syscall. The operating system unlinks the file pointer in 1 millisecond with zero WAL row generation and zero disk fragmentation!

Cassandra / ScyllaDB: Time Window Compaction Strategy (TWCS)

In NoSQL systems like Apache Cassandra or ScyllaDB, tables use Time Window Compaction Strategy (TWCS). Cassandra writes data into immutable SSTables grouped by hour. Every row has a column-level TTL (`USING TTL 86400`). Once all rows in an SSTable exceed the TTL, Cassandra drops the entire SSTable file in $O(1)$ without writing tombstones!

6. WhatsApp Status vs. Instagram Stories: Architectural Differences

Dimension Instagram Stories WhatsApp Status
Encryption Server-side TLS & application-layer auth. Meta servers have full access to story metadata. End-to-End Encrypted (Signal Protocol). WhatsApp servers cannot read media keys or status text.
Storage Location Meta CDN (Haystack/F4) + Centralized Redis & Cassandra clusters. Ephemeral server queue until delivered; permanently stored on local device storage (SQLite).
Expiration Driver Edge CDN Cache-Control + Redis TTL + Kafka Timing Wheels + Partition Drops. Client-side SQLite queries (`DELETE WHERE timestamp < now - 24h`) and device file garbage collection.
Viewers Sync Real-time pull/push from Instagram metadata microservices. Cryptographic read-receipt messages sent directly between peer contact devices.

7. Summary & Engineering Key Takeaways

  • No Global Cron Deletes: Never run periodic DELETE WHERE created_at < ... across high-volume production tables.
  • Lazy Expiration First: Filter expired items logically at read-time in API gateways and cache layers ($O(1)$ timestamp check).
  • Leverage Redis Dual Eviction: Redis pairs passive $O(1)$ lazy deletions with active probabilistic random sampling to clean expired keys safely.
  • O(1) Partitions over Row Deletions: Organize time-series ephemeral data into hourly/daily table partitions and use DROP PARTITION to reclaim disk space instantly.
  • Hierarchical Timing Wheels: For asynchronous side-effects, timing wheels scale to millions of timers with $O(1)$ insertion and trigger complexity.
