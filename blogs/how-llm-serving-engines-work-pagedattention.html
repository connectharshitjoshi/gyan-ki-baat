How LLM Serving Engines Achieve 10x Throughput: Inside PagedAttention & KV Caching

Harshit Joshi

Gyaan Ki Baat #14 • 15 min read • Published Aug 2026

When running Large Language Models (LLMs) like LLaMA 3, Mistral, or DeepSeek in production, serving infrastructure behaves completely differently from traditional web services. Under high traffic, server GPUs don't typically run out of compute power (FLOPs) — they run out of High-Bandwidth Video RAM (VRAM) due to the Key-Value (KV) Cache.

Until recently, naive LLM inference engines wasted up to 80% of GPU memory on fragmentation and over-allocation. The breakthrough that changed the entire AI industry is PagedAttention (introduced by UC Berkeley's vLLM project), which borrowed a 60-year-old operating system concept: Virtual Memory Paging.

Figure 1: Traditional Fragmented GPU VRAM vs. Optimized Paged Memory Blocks in vLLM PagedAttention engine.

1. The Anatomy of Autoregressive LLM Inference

To understand why memory is the bottleneck, we must look at how Transformer models generate text:

  1. Prefill Phase (Prompt Processing): The model takes the entire input prompt (e.g., 500 tokens) and computes attention across all tokens in parallel. This phase is compute-bound.
  2. Decode Phase (Token Generation): The model generates output text one token at a time sequentially. To generate token $T_{n}$, it must attend to all previous tokens $T_1, T_2, \dots, T_{n-1}$. This phase is memory-bandwidth bound.

Without caching, generating token 100 would require recalculating attention keys and values for tokens 1 through 99. To prevent this quadratic compute explosion, we store the intermediate Key and Value tensors for all previous tokens in GPU memory — this is the KV Cache.

2. The KV Cache Math: Why VRAM Disappears

Let's calculate the memory required for the KV Cache for a single 13B parameter model (16-bit FP16 precision):

KV Cache Formula 
Memory per Token = 2 × (Layers) × (Heads) × (Head Dimension) × (Bytes per Element)

For a 13B model (40 layers, 40 heads, 128 dim, 2 bytes FP16):
Memory per Token = 2 × 40 × 40 × 128 × 2 bytes = 819,200 bytes ≈ 800 KB / token

For a sequence of 4,096 tokens:
Total KV Cache per request = 4,096 × 800 KB ≈ 3.2 GB of VRAM!

If you handle 30 concurrent requests:
30 × 3.2 GB = 96 GB of VRAM just for the KV Cache alone!

3. The Traditional Flaw: Massive Memory Fragmentation

In naive systems (like standard PyTorch or HuggingFace Transformers), the inference engine doesn't know in advance how many tokens a user will generate. Will the response be 50 tokens or 4,000 tokens?

To avoid dynamic GPU allocations during execution (which cause massive CUDA synchronization overhead), naive engines pre-allocate a contiguous memory buffer for the maximum sequence length (e.g., 8,192 tokens) upfront.

Fragmentation Type How It Happens Impact on GPU Memory
Reserved Memory Waste Pre-allocating for max sequence length (e.g. 8K tokens) when the actual answer is only 200 tokens. Up to 70% of VRAM sits idle and cannot be used by other concurrent requests.
Internal Fragmentation Allocating memory in large power-of-two chunks that are only partially filled. Unusable gaps inside memory allocations.
External Fragmentation Requests finish at different times, leaving scattered free memory pockets too small for a new request. Server crashes with CUDA Out of Memory even with 25% total free VRAM.

4. How PagedAttention Works: Virtual Memory for GPUs

Operating systems solved this exact problem in the 1960s with Virtual Memory Paging. Instead of demanding a huge contiguous physical memory block for each program, the OS partitions RAM into small 4KB pages and maintains a Page Table to translate virtual addresses to physical pages scattered anywhere in RAM.

PagedAttention applies this exact architectural paradigm to the LLM KV Cache:

  • Fixed-Size KV Blocks: GPU memory is divided into fixed-size physical blocks (e.g., each block holds the Key and Value vectors for 16 tokens).
  • Non-Contiguous Allocation: As a user prompt generates new tokens, new KV blocks are dynamically allocated from a central memory pool. Tokens 0–15 might live in Block #4, while tokens 16–31 live in Block #92.
  • Logical-to-Physical Block Table: A lightweight lookup table maps each request's continuous token indices to arbitrary physical blocks in GPU VRAM.

5. The Game Changer: Memory Sharing & Zero-Copy Branching

Because memory is managed in discrete blocks with pointers, PagedAttention enables revolutionary memory sharing patterns with zero data duplication:

Feature How Traditional Serving Handles It How vLLM PagedAttention Handles It
Shared System Prompts Copies the 2,000-token system prompt KV Cache for every single user session. All users share the exact same physical KV blocks via read-only pointers. 0 MB extra memory!
Parallel Sampling (Best-of-N) Spawns N separate requests, duplicating the prompt N times in VRAM. Prompt blocks are shared. Forked generation uses Copy-on-Write (CoW) only when tokens diverge!
Continuous (Iteration-Level) Batching Waits for the slowest request in a batch to finish before inserting new requests (Static Batching). New requests join immediately on the next token iteration; completed requests release blocks instantly.

6. Real-World Code: High-Throughput Serving with vLLM

Deploying a high-throughput OpenAI-compatible LLM endpoint using vLLM in Python:

serve_llm.py (vLLM Production Setup) 
from vllm import LLM, SamplingParams

# Configure sampling parameters
sampling_params = SamplingParams(
    temperature=0.7,
    top_p=0.95,
    max_tokens=512
)

# Initialize vLLM with PagedAttention and dynamic KV cache allocation
llm = LLM(
    model="meta-llama/Meta-Llama-3-8B-Instruct",
    gpu_memory_utilization=0.90,     # Allocate 90% of GPU VRAM to Paged KV Blocks
    max_num_seqs=256,                 # Serve up to 256 concurrent requests per GPU
    max_model_len=8192,
    tensor_parallel_size=1
)

# Prompts sharing common system instructions
prompts = [
    "System: You are an expert system architect.\nUser: Explain Redis eviction policies.",
    "System: You are an expert system architect.\nUser: How does Kafka achieve high write throughput?"
]

# Generate tokens with zero prompt duplication
outputs = llm.generate(prompts, sampling_params)

for output in outputs:
    print(f"Generated text: {output.outputs[0].text[:100]}...")

7. Architectural Benchmark: Throughput & Latency

  • Memory Waste Reduction: Drops from >70% down to under 4%.
  • Batch Size Capacity: Increases concurrent batch capacity by 4x to 8x on the same GPU hardware (e.g. NVIDIA A100/H100).
  • Token Generation Speed: Delivers 2x to 4x lower Time-To-First-Token (TTFT) and up to 10x higher overall serving throughput (tokens/sec/dollar).

8. Summary & Engineering Takeaways

  • The Real Bottleneck: LLM serving at scale is bound by GPU memory capacity and bandwidth, governed primarily by the expanding KV Cache.
  • PagedAttention Paradigm: By splitting KV Cache into small, non-contiguous blocks and using page tables, memory fragmentation is eliminated.
  • Zero-Copy Architecture: Shared prompts, multi-candidate sampling, and continuous batching allow dramatic cost savings on expensive cloud GPUs.
