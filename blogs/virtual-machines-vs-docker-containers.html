Virtual Machines vs. Docker Containers Under the Hood: Why Containers Boot in 200ms

Harshit Joshi

Gyaan Ki Baat #11 • 14 min read • Updated Aug 2026

Why does launching a new Virtual Machine take 45 seconds and eat up 4GB of RAM, while a Docker container spins up in 200 milliseconds and uses barely 20MB? The secret lies in a fundamental realization: Containers are NOT mini virtual machines—they are just isolated Linux processes sharing the host kernel.

Figure 1: Architectural comparison between Hardware Virtualization (VMs with Hypervisor) and Containerization (Shared Host Linux Kernel).

1. The Virtual Machine Model: Hardware Virtualization

A Virtual Machine relies on a Hypervisor (e.g. VMware ESXi, KVM, VirtualBox) to simulate physical hardware: virtual CPUs, virtual memory controllers, and virtual network interface cards (NICs).

Because the hypervisor emulates real hardware, every single VM must boot its own complete Guest Operating System kernel, system drivers, systemd daemon, and package manager.

  • Memory Bloat: Running 10 VMs means loading 10 separate OS kernels into RAM (costing 10GB+ before your app even runs).
  • Slow Startup: Booting a full OS kernel and system services takes 30 to 60 seconds.

2. The Docker Secret: The Three Linux Pillars

Figure 2: The 3 Linux Pillars of Docker (Linux Namespaces, Control Groups cgroups, and Layered OverlayFS).

Docker does not emulate hardware. All containers on a host run directly on the single host Linux Kernel. Isolation is achieved using three built-in Linux kernel primitives:

1. Linux Namespaces (What a Container Can See)

Namespaces give each container its own private illusion of an isolated computer:

  • pid (Process ID): Process #1 inside the container is your app, isolated from the host process table.
  • net (Network): Each container gets its own virtual network card, IP address, and port bindings.
  • mnt (Mount): Container sees only its own root file system.
  • ipc / uts: Isolated inter-process communication and hostnames.

2. Control Groups / cgroups (What a Container Can Use)

cgroups enforce strict resource limits so a single buggy container cannot crash the entire machine: 

# Limit container to exactly 512MB RAM and 1 CPU Core
docker run -d --memory="512m" --cpus="1.0" my-node-app

3. OverlayFS (Copy-on-Write Storage Layers)

Docker images are built from immutable layers. If you run 50 containers from the same node:18-alpine base image, Docker stores the base image only once on disk. Each running container gets a tiny, lightweight writable layer on top!

3. Comparison Table: VMs vs. Containers

Feature Virtual Machines (VMs) Docker Containers
Virtualization Level Hardware Level (Hypervisor) OS / Kernel Level
Operating System Full Guest OS per VM (Heavy) Shares Host Linux Kernel (Light)
Boot Time 30 seconds to 2 minutes 50ms to 500ms
Memory Overhead Gigabytes (GBs) Megabytes (MBs)
Isolation Boundary Hardware hypervisor boundary (Very High) Linux namespace boundary (High)
Best Use Case Running different OSes (Windows on Linux), multi-tenant cloud security Microservices, CI/CD, rapid horizontal auto-scaling

4. Summary & Key Takeaways

  • VMs virtualize hardware: Great for running completely different operating systems with strong hardware security isolation.
  • Containers virtualize the OS: Lightweight Linux processes isolated via Namespaces, constrained by cgroups, and layered with OverlayFS.
  • The 200ms advantage: Starting a container is simply executing a fork/exec process call on the host kernel—no OS boot sequence required!
