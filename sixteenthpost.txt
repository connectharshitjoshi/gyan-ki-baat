☕ Gyaan Ki Baat: How Instagram & WhatsApp Stories Expire in 24 Hours (Does a Cron Job Actually Run?) ⏳📱🔥

500+ Million people post over 1 Billion ephemeral Stories & Status updates on Instagram & WhatsApp every day.

Exactly 24 hours later, the story disappears from feeds worldwide.

If you ask most engineers how this works, the default answer is:
"A cron job runs every minute and executes:
DELETE FROM stories WHERE created_at < NOW() - INTERVAL '24 hours';"

❌ Why this cron approach crashes production databases at scale:
• Locking contention across millions of rows blocks active writes and timeline queries.
• Floods Write-Ahead Logs (WAL/binlog), causing massive replication lag on read-replicas.
• In MVCC databases (Postgres), DELETE writes dead tuples, triggering nonstop I/O vacuum spikes.
• Creates brutal "Thundering Herd" CPU spikes at the top of every minute.

So how do Meta, WhatsApp, and Instagram actually expire 1 Billion stories effortlessly? 

Here is the real 4-tier distributed architecture: 🧠👇

1️⃣ Tier 1: Lazy Expiration (Read-Time Soft Filtering)
The #1 rule of high-throughput systems: "Never do background work if you can defer it to read-time."
When fetching feeds, the API gateway queries: `WHERE expires_at > NOW()`.
If a story's timestamp has passed, it is omitted on-the-fly in O(1).
Simultaneously, CDN Edge caches use dynamic `Cache-Control: max-age={expires_at - now()}` so edge nodes automatically evict media files without any origin purge signal!

2️⃣ Tier 2: In-Memory Redis TTL (Passive + Probabilistic Sampling)
Story metadata in Redis uses an 86400s TTL. Redis handles millions of keys using a dual eviction strategy:
• Passive: When a key is requested, Redis checks its timestamp and drops it if expired.
• Active Probabilistic: 10 times/sec, Redis samples 20 keys with TTL and purges expired ones, repeating if >25% are expired (capped at 25ms to prevent event-loop stalls).

3️⃣ Tier 3: Hierarchical Timing Wheels (Kafka Event Triggers)
For mandatory side-effects (archiving to User Memories, updating viewer analytics, clearing graph pointers):
Instead of an O(log N) min-heap timer queue, systems use Hierarchical Timing Wheels (Kafka/Netty) to schedule exact expiration triggers in O(1) constant time, dispatching background Kafka events to worker fleets.

4️⃣ Tier 4: O(1) Time-Partitioned Database Drops (Zero WAL Bloat!)
To permanently reclaim disk storage:
Databases use Range Partitioning (e.g. `stories_2026_08_27_hour_14`).
Instead of running millions of slow DELETE statements, the orchestrator simply runs:
`DROP TABLE stories_2026_08_27_hour_14;`
This executes an instantaneous OS file unlink() in 1ms with ZERO WAL row-logging and ZERO fragmentation!
